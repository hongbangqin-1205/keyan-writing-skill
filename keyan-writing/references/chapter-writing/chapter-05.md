# 第五章 项目建设方案（章节总纲）

**跨项目口径优先**：本文件中引用的潍坊系统、75 万字、70 万字、700/3200 功能点、固定 H7/H8
等数字和示例只是原项目参考，不构成新项目硬性下限。5.6 固定，5.6.N 名称和数量由当次建设方案
的系统清单确定；深层级由实际证据语义决定。不得照搬下方示例目录或为满足深度虚构功能点。

本章回答"具体怎么建"，把第三章的需求和建设内容落到技术方案、系统设计、部署、安全、运维等
可实施层面。篇幅、标题数量和功能点数量全部按当次建设方案确定；内容较大时按系统分次生成，
内容较小时可按完整小节一次生成，不设置跨项目统一字数或标题下限。

## 与前几章的本质区别

| 维度 | 第一~四章 | 第五章 |
|---|---|---|
| 量级 | 按章节证据确定 | 按本项目系统数量和证据确定 |
| 写作单位 | 一个章节 | **一个系统或领域**，必要时再下钻模块 |
| 组织方式 | 单草稿 | **主清单销号 + 分次写 + 合并装配** |
| 证据源 | SRC/KB 素材卡 | 建设方案的**预算清单表**（功能点硬证据）+ 正文 |

## 章节结构（13 个 H2 小节）

| 序 | 小节 | 类型 | 规模 | 拆分单位 |
|---|---|---|---|---|
| 1-5 | 总体架构/业务架构/数据架构/网络拓扑/技术路线 | 架构总览（图+简述） | 约 4000 字 + 架构图 | 各一节，一次写完 |

前 5 节的**架构图提前做好**（用户提供 pptx），正文只写文字；第 6 节是全文核心，按"领域→系统"拆分。

## 核心机制一：主清单（销号表，唯一真源）

写作前必须建立**第五章主清单**，它是一棵"领域→系统→模块→子模块→功能点"树，是拆分、分次写、
进度追踪、合并校验的唯一真源。没有主清单不得开写。

### 功能点的权威证据：预算清单表

信息化项目的功能点**必须逐条定价**，所以功能点清单的权威来源是建设方案的**软件开发预算清单表**
（附表1-6 一类），结构通用：

```
<表标题/合并单元格>            ← 系统锚
序号 | 层级模块列... | 功能描述 | 工作量(人月) | 人月单价 | 模块总价
```

"功能描述"列之前的模块列是层级路径（系统→模块→子模块→功能点），之后是工作量/价格。

### 抽取脚本（高召回候选，agent 确认）

```bash
python scripts/extract_checklist.py --source <建设方案.docx> --out docs/chapter_05/主清单候选.json
python scripts/extract_checklist.py --source <建设方案.docx> --out docs/chapter_05/主清单候选.md --format md
```

脚本**只召回候选**（path 路径 + 功能描述 + 工作量 + 表标题），不强行定层级。因为不同领域/不同
行业层级是漂移的——例：健康大脑的功能点路径首列是系统（`数据中枢→…`），提服务的系统名在表
标题里、路径首列是模块（`居民端→一键登录→…`）。**层级归一由 agent 做**，脚本保证"高召回不遗漏"。

### 主清单落盘（agent 归一后）

agent 把候选归一为销号表，`docs/chapter_05/主清单.md`：

```markdown
# 第五章主清单
| 领域 | 系统 | 模块 | 子模块 | 功能点 | 来源 | 状态 |
|---|---|---|---|---|---|---|
| 数智潍坊健康大脑 | 数据中枢 | 数据基础底座 | 数据集成工具 | 数据集成监控看板 | 附表1 | 待写 |
```

- 领域(H3)、系统(H4) 由 agent 从 path + 表标题 + 正文语义归一；模块/子模块的层级映射见
  `chapter-05-checklist-template.md`「归一规则」（中间层数不固定，折叠到 H6 模块 + H7 子模块）；
- 功能点(H8/H9) 是叶子，逐个对应预算清单一行，**不合并、不省略**；
- "状态"列（待写/写作中/已写/已校验）支撑分次写不丢进度。

## 核心机制二：系统级文件拆分

```
docs/chapter_05/
├─ 主清单.md                      # 销号表（唯一真源）
├─ 01-前5节.md                    # 总体/业务/数据架构、网络拓扑、技术路线（图+简述）
├─ 06-系统设计方案/
│   ├─ 数智潍坊健康大脑/
│   │   ├─ 数据中枢.md            # 一个系统一个文件（自包含，带锚点）
│   │   ├─ 业务中枢.md
│   │   ├─ 能力中枢.md
│   │   └─ 综合分析决策中心.md
│   ├─ 提服务/健康潍坊智慧服务平台.md
│   ├─ 提服务/健康画像.md
│   └─ …
└─ 07-后7节.md                    # 接口/安全/共享/网络/备份/部署/运维
```

- **基本写作单元 = 一个系统（H4）**，一个系统一个 md 文件，自包含（总体架构/功能架构/数据架构/系统功能设计），
  可独立写、独立校验、独立评审；
- 大系统（数据中枢、业务中枢等超 8 万字）下钻到**模块**分文件（`数据中枢/数据集成工具.md`）；
- **标题层级不机械固定**：项目目录实例从当次建设方案复制经确认的来源子树；标题层级按系统、模块、
  子模块和功能点的实际语义重挂。只有来源证据存在时才继续下钻，不为达到 H7/H8 人工补层级。

## 核心机制三：分次写 + 状态追踪

第五章必须分多次写。每次：

1. 从主清单挑一个"待写"系统（或模块），读其对应的预算清单行 + 正文段落；
2. 写该系统 md（功能点逐个销号，锚点标 `〔SRC-xxx〕`，工作量的行号定位记 sidecar）；
3. 写完把主清单里该系统状态改为"已写"，跑系统级 `check-depth --scope` 校验；
4. 下次继续下一个系统，**状态只存主清单，不靠 agent 记忆**。

## 核心机制四：合并装配

全部系统写完后：

1. 按"领域→系统"树序把各系统文件拼成第 6 节，再与 01、07 合为整章；
2. `assemble` 装配 + 章级 `check`（来源一致性、草稿完整性、显式缺口和重复内容）；
3. 缺少来源系统、功能点或必要正文的，回主清单补证据或保留 `GAP`。

## 深度契约（profile `depth_contract.chapter_05`）

- `min_function_points`：功能点总数下限（默认 700，本项目级按预算清单实际数量校准）
- `function_point_level: 6`：**章级口径**——H6 及更深标题都计入 `min_function_points`（衡量标题丰富度）；
  系统级自检另用 `function_point_level: 8` 只数 H8 功能点（精口径，见 06 节"系统级自检"），两者用途不同，不混用
- `domain_parent: 系统设计方案`：H2"系统设计方案"下的 H3=领域、H4=系统
- `min_domains`：领域数下限；`min_leaf_chars`/`max_thin_leaves`：功能点叶子正文不得过薄
- 交付深度以本项目证据为准：可止于系统或模块，也可展开到功能点；不得因通用模板强制到 H7/H8。

## 写作要点

- 逐系统、逐功能点生成，一次只写一个系统或模块，不合并
- 系统名称、功能清单、接口、性能指标必须来自证据（预算清单 + 正文），不得虚构
- 现状系统与规划系统区分清楚，不把规划写成已建成
- 功能点的"功能名 + 功能描述"与预算清单一致；工作量/单价登记 sidecar，不在正文堆金额
- 技术方案与第三章建设内容、第四章部署、第七章投资口径一致
- 架构用文字分层描述（标题+列表/表格），不画图、不写代码；前 5 节图用用户提供的 pptx

## 通用要求

正式书面语；系统设计用规范术语；正文不加引用标记，来源记 sidecar；不写手工章节编号。
