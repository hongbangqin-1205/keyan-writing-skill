# 可研编写工作流（收集 → 计划 → 起草 → 校验 → 评审 → 发布）

本文件是可研编制的**主流程**：规定每个阶段的输入、产物与门禁，以及四类信息源
（本地文件 / 知识库 / 网络检索 / 模型知识）的使用规则。`SKILL.md` 的命令清单是本流程
各阶段的工具。

核心原则：**先收集、再计划、后动笔；每一段要么有锚点，要么标推导，要么显式标缺口。**

真实项目的编写顺序（与交付目录一致）：

```
调研报告（人工调研产物，可研输入）
建设方案（含已确认子系统方案，可研输入）      ──先写──> 第五章各领域子系统
估算表/预算清单                              ──支撑──> 投资与功能点清单
                                              ──后写──> 其余章节（围绕第五章补齐）
```

即**子系统先行，其他章围绕它补齐**，而不是从第一章顺着写到第十一章。

## 阶段总览

| 阶段 | 产物 | 主要命令 | 门禁 |
|---|---|---|---|
| P0 立项与基线 | `project.json`、`fact_baseline`、`duplication.whitelist` | `template`、`validate-outline` | 元数据齐备；口径基线非空 |
| P1 素材归一化 | `extracted/`（全量抽取）、`文件清单.md`（文件画像）、`normalized/`（SRC-/KB-/WEB-）、`manifest.json`、`evidence.json` | `validate-evidence` | 来源分类齐备；hash 一致 |
| P2 章节资料包 ★ | `docs/<节点>/素材卡.md`（可拆分合并） | `validate-dossier` | **硬门禁**：每小节 ≥1 素材卡或显式缺口 |
| P3 内容计划 | `docs/<节点>/计划.md` | `validate-plan` | 每节点有来源或推导；推导率达标；体量达下限 |
| P3.5 小节正文大纲 | `docs/<节点>/大纲.md` | — | 每小节有目的、必写要素、证据映射、结构、篇幅和扩展点 |
| P4 起草（两轮） | `docs/<节点>/草稿.md`（带锚点）+ `丰富记录.md` | — | 第一轮就写全写足；第二轮查漏补缺、必要时扩展检索 |
| P5 确定性校验 | 校验报告 | `check-depth`/`check-provenance`/`check-duplication`/`check-features`/`check-baseline`/`self-check` | 全部 `valid` 或缺口显式化 |
| P6 独立评审 | `issues.json` + 修订 | 人/独立代理 | 抽样反证锚点；数字、文风、流畅性达标 |
| P7 装配发布 | 章节 + sidecar + DOCX | `assemble`/`register-chapter`/`check-chapter`/`report` | hash、深度、空标题、归属、**资料包**全过 |

正文**不在素材卡后一次成稿**：先写小节正文大纲，再完成第一轮就**写全写足**的基础稿；第二轮只做查漏补缺——
检查遗漏要素、补齐表格、统一文风、校正口径，本地缺政策/标准/技术资料时才扩展检索后再补写。
最终文风由第二轮与 P6 独立评审共同验收。

## 四类信息源的使用规则

| 信息源 | 用途 | 证明形式 | 硬规则 |
|---|---|---|---|
| **本地项目文件**（调研报告、建设方案、子系统方案、估算表、名单） | 项目事实 + 本地已有政策/标准/技术方案 | `SRC-` 素材卡 → 锚点 | 本地已有且足够时**优先使用**，不被未核验的外部资料覆盖 |
| **知识库**（consulting-kb-retrieval） | 政策文号、标准版本、法规施行日期（**政策密集章第 1、2 章必查，以 KB- 卡为主**）；本地不足或扩展时的技术方案、本项目历史版本、模板结构 | 命中片段落盘为 `KB-` 卡（出处=库名/文档/页码） | 政策/标准/法规日期必须查 KB，本地清单只能核验不能替代；案例数字须核实后再用 |
| **网络检索** | 最新政策、标准版本、公开技术资料、公开可核实事实 | 快照落盘 `WEB-` 卡（网址+检索日期） | **默认关闭**；outline 声明 `web_search: true` 或用户明示才启用 |
| **模型自身知识** | 结构、文风、方法论、通用技术原理、架构分层、流程设计 | `〔推导：依据〕` | 可用于技术扩展；不得生成未经证据支持的项目事实 |

**本地优先，政策必查**：
- 项目事实（人名、金额、地点、现状、建设内容）本地正式材料优先；知识库/网络仅作版本核对或本地不足时的补充。
- 政策文号、标准版本、法规施行日期**必须查知识库**——本地清单只能核验、不能替代；政策密集章（第 1、2 章）以 KB- 卡为主。
- 技术方案本地优先；本地不够详细时查知识库，最新版本与公开技术资料可查网络。
- 技术内容本地与检索资料都不足时，允许模型通用知识做设计推导，但必须标 `〔推导：依据〕` 及适用前提。

**落盘约定**：KB 与 WEB 命中必须先存为 `normalized/` 下的文本文件
（命名如 `KB-001_政策法规__国办发2021_18号.txt`、`WEB-001_三级医院评审标准2022.txt`，WEB 文件首行
注明 URL 与检索日期），登记进 `manifest.json` 之后才能被锚点引用。**未落盘的资料不得写进正文。**

## 工作区布局（docs/ 为编写界面，md 是唯一真源）

```
<project>/
├── outline.json / manifest.json / evidence.json    # 全局契约（机器层）
├── extracted/             # 全量抽取文本（临时工作区，不入池、不进 manifest、不参与装配；生成确认后可删）
├── 文件清单.md            # 文件画像：每份用户文件是什么、含什么、是否入池（便于后续查阅）
├── normalized/            # 归一化素材池（SRC-/KB-/WEB-，全局共享、按 id 检索、不按章复制）
├── docs/                  # ★ 人读的编写工作区（agent 写、人可审）
│   ├── 写作指南.md         #   全局：文风纪律、锚点约定、写作顺序
│   ├── 事实基线.md         #   全章共用口径（可读版）
│   └── chapter_05/        #   每章一个目录（单节作业则 chapter_05_06/）
│       ├── 计划.md         #   编写计划（P3 产物，md 格式）
│       ├── 素材卡.md       #   收集成果（P2 产物，md 格式）
│       ├── 大纲.md         #   小节正文大纲（P3.5 产物，md 格式）
│       ├── 草稿.md         #   两轮起草后的带锚点正文
│       ├── 丰富记录.md     #   第二轮检查、检索、扩写记录
│       └── 素材卡-提服务.md #   大章可拆分，加载时自动合并（素材卡.md 恒排最前）
├── work/                  # 机器产物（features.json、sections/ 等，不手改）
├── chapters/              # 发布产物 + sidecars
└── context/               # 登记
```

`extracted/` 与 `文件清单.md` 是**工作文件**：extracted 存放全量抽取的纯文本，供文件画像和
第二轮 BM25 检索原始细节使用，不入池、不进 manifest、锚点不引用；生成确认完成后可整体删除。

四条放置原则：

1. **按章聚合**：写第五章只开 `docs/chapter_05/` 一个目录——计划、卡、草稿都在手边
2. **全局池共享**：`normalized/` 按 id 存，同一 SRC 可被多章引用，绝不复制多份
3. **卡指向池**：卡上只写 `来源: SRC-007`；正文锚点沿用，草稿可由卡回溯到原文
4. **md 是唯一真源**：素材卡与计划都是 md，校验器直接解析 md；json 仅作编程兼容入口，
   工作区里不出现第二份产物（结构上不可能漂移）

## P1 素材归一化

归一化分三步：**全量抽取 → 文件画像 → 按需入池**。三步职责不同，不可混为一谈：

### 1. 全量抽取（机械，全量）

把用户提供的所有可解析文件（docx/xlsx/pdf）一次性转成纯文本，落到 `extracted/` 临时区。
抽取是机械、便宜、可复用的：文档正文远比图片小，全量抽取不会显著占空间。

- 只抽正文与表格文本；图片、页眉页脚不落盘；
- 纯扫描 PDF 需先 OCR，无法 OCR 的标为"不可解析"并在文件画像中说明；
- `extracted/` 不入池、不进 `manifest.json`、锚点不引用，生成确认完成后可整体删除。

### 2. 文件画像（判读，全量文本上一遍成）

基于 `extracted/` 的文本，产出一份 `文件清单.md`，逐份说明：

```markdown
| 文件名 | 是什么 / 含什么 | 是否入池 | 入池后 id / 不入池原因 |
|---|---|---|---|
| 建设方案v8.4.docx | 项目建设内容、目标、预算、工期 | 是 | SRC-001 |
| 调研报告v5.0.docx | 现状、问题、对策 | 是 | SRC-002 |
| 三定.pdf | 卫健委职能配置 | 是 | SRC-003 |
| 某投标文件.docx | 与本项目无关的旧版 | 否 | 版本过旧 |
```

**判断"是否关键"的写法（不精读全文，尤其大文件）：**

按顺序看三样东西，足够判断即可，**禁止逐字通读大文件**：

1. **文件目录 / 章节大纲 / 封面**：docx 的目录与章节标题、封面的名称与版本，前几十行就能定性；
   xlsx 看表头行与 sheet 名；PDF 看首页与目录。
2. **文件名 + 类型归类**：建设方案、调研报告、估算表、批复/可研、三定/名单 → 直接判关键；
   过程稿、旧版本、无关项目 → 判无关。
3. **抽样抽查**：拿不准的文件，用 `local_search.py` 或 read 抽看开头 + 目录 + 结尾，确认它讲什么，不必通读。

**判断粒度是"文件级"，不是"内容级"：** 一份文件要么整份入池、要么整份不入池，
不存在"从大文件里抠段落入池"。因为入池是"整份落盘 + 登记一个 id"，后续锚点按 id 引用整份来源；
抠取相关段落是第二轮查细节时才用 `local_search.py` 做的，不在画像阶段。

文件画像是后续查阅的索引，也用于判断哪些文件入池，不必逐个 read 二进制。

### 3. 按需入池（挑选，按 outline 需求）

以 `outline` 的 `recommended_items` 为需求清单，把**关键文件**正式归入 `normalized/`
（`SRC-xxx.txt`），登记 `manifest.json`；KB/WEB 命中片段落盘 `KB-/WEB-xxx.txt` 并登记。
入池要控噪声：只入关键文件，无关/过旧文件留在 `extracted/` 供第二轮按需检索即可。

## P2 章节资料包（dossier，硬门禁）

写作前先把本章素材收集、蒸馏成 `docs/<节点>/素材卡.md`（严格文法：每卡一个 `##` 块 + 固定字段）：

```markdown
# 素材卡 · chapter_05_06

## C001 健康大脑现状摘录
- 来源: SRC-007
- 定位: L12-L40
- 摘录: 全市已建成市、县两级全民健康信息平台，按互联互通四级甲等标准建设，汇聚健康医疗数据……（≥40字）
- 关键数字: 45亿条；229张表
- 用于: 系统设计方案

## C002 编制依据·国办发18号
- 来源: KB-001
- 出处: 01_政策法规与标准 / 国办发〔2021〕18号 / p2
- 摘录: 推动公立医院高质量发展，强化信息化支撑……
- 用于: 编制依据

## C003 评审标准版本
- 来源: WEB-001
- 网址: https://example.gov.cn/standard
- 检索日期: 2026-09-14
- 摘录: 《三级医院评审标准（2022年版）》……
- 用于: 系统设计方案

## GAP-01 网络拓扑
- 原因: 未获得专网拓扑资料
- 需要: 拓扑图或组网说明
```

字段表（固定，不做同义词）：素材卡用 `来源/定位/摘录/用于/关键数字/出处/网址/检索日期`；
缺口条目（id 以 GAP 开头）用 `原因/需要`。解析器按行报错
（`md_unparsed_line`/`md_unknown_field` 带行号），格式错误过不了门禁。

**门禁（`validate-dossier`）**：

- 每个小节 ≥ `min_cards_per_section` 张卡（默认 1），**或**有 GAP 条目显式声明缺口
- 摘录 ≥40 字；`用于` 必须指向真实小节
- `来源` 必须 `SRC-/KB-/WEB-` 前缀；KB 卡须带 `出处`（库名/文档/页码）；
  WEB 卡须带 `网址+检索日期`，且 outline 已开 `web_search`
- **无资料包不得起草**：`assemble` 在 `dossier.required`（profile 默认 true）时
  找不到或校验不过即拒绝发布；确需跳过要显式声明 `dossier: {"required": false}` 留痕

**收集步骤**（agent 执行）：

1. 读 profile 本章规范与 `事实基线.md`，列出本章小节与模板子项清单
2. 从 `normalized/` 筛选与本章相关的 SRC 文件，摘录成卡（记录定位与关键数字）；
   `normalized/` 里没有但 `extracted/` 里有原文时，用 `local_search.py` 检索原文后补卡
3. **政策密集章（第 1、2 章）必查知识库**：政策文号、标准版本、法规施行日期以 KB- 卡为主，
   本地政策清单只能核验、不能替代；其他章在本地缺政策/标准/技术时也查知识库补 KB 卡
4. **本地优先**：项目事实与本地已有的政策/标准/技术方案直接制卡；本地不足时登记待补项
5. 技术方案本地不足时查知识库，最新版本或公开技术资料（已授权）查网络，命中先落盘 KB/WEB 卡
6. 仍缺且用户已授权 → 网络检索补 WEB 卡（快照落盘）；技术资料仍不足可用模型通用知识推导并标记
7. 项目事实仍缺失的写 GAP 条目，**不编造**
8. `validate-dossier --dossier-path docs` 通过后进入 P3；大纲完成后进入第一轮起草（第一轮就写全写足）

## P3 内容计划

素材卡就绪后写 `docs/<节点>/计划.md`（同为 md 文法，每节点一个 `##` 块）：

```markdown
# 计划 · chapter_05

## 05.06.提服务.健康潍坊智慧服务平台
- 层级: system
- 父: 05.06.提服务
- 归属: 系统设计方案
- 来源: SRC-018, SRC-021
- 目标字数: 42000

## 05.06.提服务.预约挂号
- 层级: function_point
- 父: 05.06.提服务.健康潍坊智慧服务平台
- 归属: 系统设计方案
- 推导: 依业务闭环与同类系统惯例推导
- 目标字数: 900
```

字段：`层级/父/归属/来源/推导/依据/目标字数`。`来源` 与 `推导` 二选一——有来源即证据节点；
写 `推导: <依据>` 即设计节点（计推导率）。门禁见 `validate-plan`；推导边界分域授权见上表。

## P3.5 小节正文大纲

素材卡与计划就绪后，先写 `docs/<节点>/大纲.md`。大纲必须按小节逐项定义：

- 本小节要回答的问题与写作目的；
- 必写要素、必写事实和不可遗漏的指标；
- 每个要素对应的 SRC/KB/WEB 卡，或明确 GAP；
- 正文组织顺序、目标篇幅和段落数量；
- 必需表格的用途、表头和最少行数；
- 第一轮就要写全写足的要素清单（按 profile 的 `item_depth` 逐项下限）；
- 第二轮查漏补缺时可能需要检索或技术推导的扩展点；
- 与其他章节的承接边界，避免重复或提前展开。

大纲不是目录，也不是先写正文再补的说明；没有小节大纲不得进入正文起草。
模板见 `references/chapter-writing/chapter-01-outline-template.md`。

## P4 起草（两轮）

段落带锚点：事实句 `〔SRC-007〕`，设计句 `〔推导：依据〕`，KB/WEB 资料用 `〔KB-001〕`/`〔WEB-001〕` 引用。
三条纪律：**不照抄**（连续重合 ≥40 字即违规，政策名称/标准号走白名单）、**不编造**（事实句必须有锚点）、
**不填空**（无证据且不许推导的写 `GAP:`，GAP 句不计入内容长度）。

### P4.1 第一轮：写全写足

第一轮就按大纲和 profile 的 `item_depth` 下限把正文**写满**，不写"骨架稿"：

- 大纲必写要素全部有正文对应，且达到各自字数下限；
- 项目事实、建设任务、系统清单、指标、政策和标准不因压缩而遗漏；
- 现状、拟建内容和预期效果分开表述；
- 已有表格、清单和量化指标按证据完整装配（绩效表、建设模式明细表、投资构成表等）；
- 政策文号、标准版本、法规施行日期以已落盘的 KB 卡为准；
- 无证据的项目事实写 GAP，不用模型知识补造。

### P4.2 第二轮：查漏补缺

第一轮完成后进行第二轮检查，并在 `丰富记录.md` 记录检查结论、检索动作和补写内容。检查维度：

- 内容是否覆盖大纲与素材卡、是否达到 `item_depth` 逐项下限；
- 是否有"只有结论没有展开"、段落过薄或系统名称堆砌；
- 背景、问题、目标、任务、内容、模式、绩效是否相互对应；
- 是否缺系统明细表、政策对应表、技术标准表或绩效指标表；
- 政策、标准和技术依据是否完整、是否缺版本/日期；
- 是否存在章节重复或口径不一致。

发现不足或需补充细节时，才按缺口扩展检索，顺序如下：

1. **本地原文检索**（`extracted/` 全量文本）：具体细节往往在原始材料里但没进 `normalized/` 池，
   用 `python scripts/local_search.py --sources-dir extracted --query "..."` 精确匹配或 BM25 找回相关段落；
2. **知识库**：政策文号、标准版本、法规施行日期、本项目历史可研/初稿；
3. **经授权的网络**：最新政策、标准、公开技术资料；
4. **技术通用知识推导**：仍无资料时用模型通用知识，标记 `〔推导：依据〕`。

KB/WEB 命中必须先落盘并登记后才能写正文；扩展后的事实句仍需锚点，模型技术推导必须标记。
检索只返回候选片段与出处，是否选用、如何落成正文由模型判断。模板见
`references/chapter-writing/chapter-01-enrichment-template.md`。

两轮之间不复制多份正文：`草稿.md` 始终是唯一正文真源，`丰富记录.md` 记录变化。
发布时 `assemble` 剥离锚点并写入 `.anchors.json`。

**单节模式**：只写某一节时，资料包/计划/契约都按节点 id（如 `chapter_05_06`）组织，
节文件命名 `chapter_05_06.md`，`--scope` 限定范围，其余节点报 `out_of_scope`。

## P5 确定性校验 / P6 独立评审 / P7 装配发布

同前：`self-check` 汇总深度/资料包/计划/出处/抄袭/口径/功能覆盖七类缺口并给出
`next_actions`；独立评审抽样反证（可显式跳过并留痕）；`assemble` 发布前执行
证据覆盖 → 深度契约 → 必需小节与子项归属 → **资料包门禁** → 锚点剥离。

## 素材不足时的部分交付

不以通用短文凑数：章节标 `partial`、输出结构化缺口清单（缺什么、需要哪类素材、影响哪节），
`report` 记录 scope 与未完成节点，素材补齐后按 `next_actions` 增量续写。

## 反模式清单

| 反模式 | 触发检查 |
|---|---|
| 未收集资料直接开写 | `validate-dossier` / assemble → `dossier_missing` |
| 某小节既无卡也无缺口声明 | `dossier_section_uncovered` |
| 素材卡格式随意（自由文本/自造字段） | `md_unparsed_line` / `md_unknown_field`（带行号） |
| KB 命中不落盘、无出处 | `dossier_kb_no_provenance` |
| 未授权用网络资料 / 无快照 | `dossier_web_unauthorized` / `dossier_web_card_incomplete` |
| 把参考可研当正文复制 | `check-duplication` → `verbatim_copy` |
| 用通用短文填满模板子项 | `duplicate_block` |
| 功能清单与正文同源 | `feature_self_reference` |
| 事实无锚点 / 推导无依据超比例 | `check-provenance`、`validate-plan` |
| GAP 句冒充内容 | `check-depth` → `empty_*` |
| 子项塞错父节 | `item_wrong_parent` |
