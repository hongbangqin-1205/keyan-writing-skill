# 系统设计方案（第五章第 6 节）

**跨项目优先规则**：5.6 的领域/系统名称和数量从当次方案识别，下方潍坊领域和 H3—H9
展示为本项目示例，而非固定模板目录或全项目硬性深度。若输入缺少相应模块，不得硬造 H7/H8；
功能点数和描述按本项目证据/预算清单核验，短描述标缺口而不编造。

本节是第五章的核心和篇幅最大节（参考可研约 70 万字、3200+ 功能点），按建设领域（H3）
逐领域展开，每个领域下按系统（H4）设计，每个系统按架构/流程/数据（H5）和功能模块（H6）、
功能点（H7/H8/H9）展开。**本节按系统拆分、分次写，先建主清单再逐系统销号**（见总纲）。

## 展开结构（硬性）

```
### 领域（数智潍坊健康大脑 / 标准体系 / 提服务 / 重整合 / 强机构 / 兴产业 / 促协同 / 辅治理 / 安全一体化平台）
  #### 系统名称（数据中枢 / 健康潍坊智慧服务平台 / 整合型医生工作站…）
    ##### 总体架构            ← 系统在整体架构中的位置（H5 架构层）
    ##### 功能架构            ← 模块划分（H5 架构层）
    ##### 数据架构            ← 数据来源、流向、存储（H5 架构层）
    ##### 系统功能设计        ← H6 模块 → H7 子模块 → H8/H9 功能点
      ###### 模块A（H6）
        ####### 子模块A1（H7）
          ######## 功能点A1-a（H8）
          ＜功能描述正文，另起一行，≥20 字＞
```

**层级语义（全文统一，不按 heading 数字机械映射）**：

- H3 = 领域，H4 = 系统，H5 = 架构层（总体架构/功能架构/数据架构/系统功能设计），H6 = 模块，H7 = 子模块，H8/H9 = 功能点；
- **交付必须到 H7**（子模块级标题完整展开），功能点（H8/H9）作为 H7 下的叶子；
- **功能点是"标题 + 正文"两行**：H8 标题 = 功能名，紧接着另起一行写功能描述（≥20 字）。
  **不得把功能点写成单行"标题：描述"**——那样深度校验会把整行当标题、叶子正文计为 0，判为过薄；
- 领域层级是漂移的：健康大脑的"系统"在"系统功能设计"H3 包裹层下（数据中枢/业务中枢/能力中枢/综合分析决策中心），
  其他领域的"系统"直接在领域 H3 下——**以证据的语义为准，不假设固定层级**。

## 功能点证据：预算清单表（必读）

每个系统的功能点**必须逐条对应建设方案预算清单表的一行**（要算钱，一个功能点都不能缺）：

- 功能点名称 = 预算清单"功能描述"列之前的最后一列模块名；
- 功能点描述 = 预算清单"功能描述"列；
- 功能点数量以预算清单为准，**不合并、不省略、不凭空加系统/功能**。

用抽取脚本召回候选（路径 + 描述 + 工作量），agent 归一到本节的层级结构：

```bash
python scripts/extract_checklist.py --source <建设方案.docx> --out 主清单候选.json
```

## 反模式（出现即视为未达标）

- ❌ 一个系统只有"功能架构/业务流程/数据架构/系统功能设计"四个 H5 标题，下面全是概括段落
- ❌ 把多个系统合并成一节，或只写"系统支持 XX 功能"而不列表
- ❌ 功能点用"等""若干"代替，不逐条列出、不逐条对应预算清单
- ❌ 用一个 H4 覆盖整个领域（领域下必须有系统）
- ❌ 功能点名称/数量与预算清单不一致（凭空增删功能点）
- ❌ 不建主清单就开写，或分次写不更新主清单状态

## 正例（节选：数据集成工具）

```
#### 数据中枢
##### 功能架构
数据中枢由数据基础底座、数据集成工具、数据开发工具、数据标准化工具、数据治理工具等模块构成。

##### 系统功能设计
###### 数据集成工具（H6 模块）
####### 数据集成总览（H7 子模块）
######## 数据集成监控看板（H8 功能点）
数据集成监控看板针对数据集成情况进行综合性展示，高效直观地展示当前数据的集成情况。
######## 数据集成概览查看（H8 功能点）
数据集成情况概览支持异常概览和集成概览等功能，能够实时展示平台中异常作业和任务，并可通过点击下钻到具体异常任务。
######## 数据集成异常查看（H8 功能点）
数据集成异常查看功能是数据集成异常展示中心，可实时展示数据集成异常信息。
```

功能点的"功能名称"与"功能描述"必须与预算清单一致（功能名可同名，靠正文描述区分，逐行保留不合并）；
工作量/人月单价登记 sidecar，不在正文堆金额。

## 写作要点

- 按领域逐个、按系统逐个、按功能点逐条生成，一次只生成一个系统或一个模块，不合并
- 建设领域和系统名称、功能清单、功能点数必须来自证据（预算清单 + 正文）
- 每个系统的写法：
  - 总体架构：系统在整体架构中的定位、与上下游系统的关系
  - 功能架构：系统包含哪些功能模块，用列表或表格，模块通常 5~10 个
  - 数据架构：数据来源、流向、存储、共享
  - 系统功能设计：按 H6 模块 → H7 子模块 → H8/H9 功能点逐条说明（输入、处理、输出）
- 现状系统与规划系统区分清楚，规划系统不写成已建成
- 功能点叶子正文 ≥ 20 字（`min_leaf_chars`），不得只剩标题

## 约束

- 系统功能设计是本节最大篇幅，功能点描述要具体（能落地到开发），不说空泛的"支持XX功能"
- 系统数量、功能清单、功能点数必须来自证据，不凭空增加系统或功能
- 涉及数据量、接口数、功能点数的数字必须来自证据
- 接口设计细节留给"终端系统及接口设计"节
- 资料中确有但零散的子系统，可归并到同类系统下并标注来源口径

## 功能点写作的边界情况（预算清单常出现，必须处理）

- **同名功能点**：同一子模块下功能点同名（如"人员详情"×3、"历史记录列表"×2），是预算清单里
  不同描述的多行，**逐行保留、不合并**，H8 标题同名靠正文描述区分；
- **同描述异名**：不同功能点描述完全相同（源清单复制错误），逐行保留、靠 H8 标题区分，不得合并也不得改描述；
- **空描述行**：预算清单"功能描述"列为空时，按功能名推导补写描述（说明输入/处理/输出），
  不编造数字；来源标 GAP 或 `〔推导：依据功能名〕`；
- **描述过短**：预算清单描述可能只有 4~6 字（如"数据导出"），达不到 `min_leaf_chars=20`，
  允许轻度扩写为"该功能支持……，用于……"，但**不得新增数字或事实**；
- **小计/总计行**：预算清单末尾的小计/合计/总计行不是功能点，抽取脚本已剔除，手工核对时也要跳过。

## 系统级自检（合并前）

单个系统 md 无法直接 `check-depth`（该命令依赖 P0 脚手架的 outline + profile）。系统级自检用：

```bash
python -c "import sys; sys.path.insert(0,'scripts'); from feasibility_core.depth import measure; \
print(measure(open('docs/chapter_05/06-系统设计方案/提服务/电子健康证明管理系统.md',encoding='utf-8').read(), function_point_level=8, leaf_min_chars=20))"
```

核对：功能点数 = 预算清单该系统行数、`thin_leaves == 0`、每个功能点都在 H7 子模块之下。
合并装配后再跑章级 `check-depth`（总字数、功能点数、领域数、每领域系统数）。

## 规范性要求（依据 2023 通用大纲）

信息化项目的系统设计对应通用大纲的"工程方案"和"设备方案"。系统设计应论述
建设标准、主要系统设计方案、关键设备（含软件）规格数量与性能参数，说明
设备（软件）与技术方案的匹配性和可靠性。系统功能设计应落到可实施的功能点，
并对关键设备进行单台技术经济论证（资料具备时）。

## 典型表述

- 「功能架构主要包括：……」
- 「业务流程：用户……，系统……，最终……」
- 「系统功能设计包含以下子功能：……」

## 完成标准（系统级，合并前每个系统都要过）

- [ ] 系统在 H4，模块 H5/H6、子模块 H7 完整，功能点 H8/H9 逐个对应预算清单
- [ ] 功能点数量 = 预算清单该系统的行数，名称与描述一致
- [ ] 每个功能点叶子有正文描述（≥20 字），无空标题
- [ ] 主清单里该系统状态已置"已写"，功能点已销号
- [ ] 系统级 `check-depth --scope` 通过
